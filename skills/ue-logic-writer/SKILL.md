## How You Work

### Before Writing Code
1. Read ALL mandatory rule files listed above.
2. Read the existing header file(s) for the class(es) you're implementing logic in — understand the declarations, types, and signatures.
3. Read any related/referenced classes to understand the APIs you'll be calling.
4. Read the existing .cpp file if it exists, to understand current implementation patterns and includes.
5. Understand the full context: what subsystems, components, and data structures are involved.

### While Writing Code

Apply ALL rules from the rule files rigorously. Key patterns you must follow (but always defer to the actual file contents):

**From General Code Rules (verify by reading the file):**
- Comparisons: always use `<` or `<=`, never `>` or `>=` — flip the operands
- Local variables: always `const` unless mutation is required
- No `while` loops — use `for` with explicit bounds
- Naming: `Set` (assign) vs `Change` (modify), `Delta` (change amount) vs `Remaining` (what's left)
- Factory methods for object creation
- Function declaration in .h, definition in .cpp — always

**From Defensive Programming Rules (verify by reading the file):**
- Validate ALL incoming parameters at function start
- Use assert macros with appropriate behavior (return, ignore, break, continue)
- Use TOptional for values that may not exist
- Every `switch` must have a `default` case
- Minimize scope — declare variables as close to usage as possible

**From Assert Macros (verify by reading the file):**
- Use the exact macro names defined in the file
- Choose the right behavior suffix (_return, _ignore, _withBreak, _withContinue) based on context
- Common patterns: `assertUObjectPointerIsValid_return` for pointer params, `assertGameplayTagIsValid_return` for tag params

### Code Quality Standards
- Write clean, readable code with clear intent
- Add comments for non-obvious logic, but don't over-comment obvious code
- Use UE5 idioms and patterns (GameplayTags for lookups, subsystems for global state, components for modular behavior)
- Prefer async loading patterns where the project uses them
- Respect the existing architecture: data-driven design, policy pattern, component-based architecture
- Use `UFUNCTION`/`UPROPERTY` specifiers correctly when modifying declarations (though prefer to only implement existing declarations)

### After Writing Code
- Verify all rule files were followed
- Check that all parameters are validated
- Ensure no `>` comparisons snuck in
- Confirm all locals that can be `const` are `const`
- Verify assert macro names are exact matches from the rules file
- Make sure .h/.cpp separation is maintained
